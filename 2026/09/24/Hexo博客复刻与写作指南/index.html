本文档以 “若璃的博客”（D:\BlogFile - 副本）为蓝本，完整记录从零复刻同一份博客的全过程：环境准备 → 建站 → 配置 → 写作 → 自检 → 部署。

所有配置片段与命令均取自该项目的真实现状，不是通用教程的复制；凡与官方默认值不同的地方，都写明了为什么改以及踩过什么坑。

0. 技术选型与成品形态

项目 取值 说明
站点生成器 Hexo 8.1.1 package.json 声明 hexo: 8.1.1
主题 hexo-theme-butterfly 5.5.4 装在 node_modules/，不在 themes/
Markdown 渲染 @upupming/hexo-renderer-markdown-it-plus 为了挂 KaTeX 插件
数学公式 KaTeX 0.16.28，服务端渲染 客户端不加载 KaTeX JS，只加载 CSS
正文字体 PingFang 简体（自子集化 woff2，1.12 MB） 非系统苹方，保证跨设备一致

搜索 Algolia（自托管前端库 + 自建干净索引） 索引正文由项目脚本产出

关键 CDN 资源 全部自托管（KaTeX、algoliasearch） 见 6.12

成品形态：

  • 首页全屏横幅 + 打字机副标题（今日诗词 API）+ 卡片流（图在左信息在右，左右交替）

  • 文章页右侧目录、代码块浅色高亮 + 复制按钮、图片点击放大（fancybox）

  • 导航栏内嵌 Algolia 搜索框，支持全文（前 3000 字符）检索
  • 有独立页面：分类总览 /categories/、标签总览 /tags/、归档 /archives/、友情链接 /link/、说说 /shuoshuo/、草稿区 /pre_post/

4. 四份配置文件各管什么

文件 作用域 什么时候必须改 改完要不要清缓存
_config.yml 站点级：URL、永久链接、渲染器、Algolia 凭据、部署 换域名、加插件、配搜索 要（删 db.json）
_config.butterfly.yml 主题级：外观与交互的全部开关 改样式/字体/横幅/菜单 要（主题 CSS 会缓存）
source/css/custom.css 自定义 CSS（经 inject.head 注入） 加 @font-face、微调样式 否（原样拷贝）
scripts/*.js 站点级 Hexo 脚本（自动加载，无需注册） 改渲染后处理逻辑 要

scripts/ 目录的机制：站点根目录下的 scripts/*.js 会被 Hexo 自动 require，无需在配置里声明。这是「不改主题源码就扩展行为」的官方途径——升级主题不会覆盖它。本项目用它来改造摘要与搜索索引。

5. 根配置 _config.yml 逐段配置

5.1 Site 与 URL（最容易埋雷的地方）

url 是必改项，且后果是隐性的。Hexo 默认值是 http://example.com，若不改：

  • 每页 <link rel="canonical"> 与 og:url 全指向 example.com
  • Algolia 索引里的 permalink 也全是 example.com → 表现为「能搜到，但点进去跳到 example.com」

部署后可用 python tools/check-search.py --live 的第 L 项直接验证索引里的域名对不对。

5.2 写作行为

post_asset_folder: true 的效果：hexo new post "一元线性回归" 会同时生成 source/_posts/一元线性回归.md 和 source/_posts/一元线性回归/。文章里写相对路径形式的图片引用（配合 hexo-image-link）就能解析到该文章的图片文件夹。

⚠️ 不要在文章里写 img 标签的字面示例：hexo-image-link 用一条正则无差别扫描全文（不区分正文与代码块），其中一条专门匹配 img 标签的 src 属性并把路径改写成「当前页面路径 + 文件名」。所以这类示例会被就地改坏，显示成你这篇文章的真实路径；正则若取不到 src 还会在构建日志里打印 img tag found。要举例请改用单引号或行内描述。

两个选项为什么不能省：

选项 写错会怎样
strict: 'warn' 写成 false 会把「LaTeX 不兼容写法」的提示全部静音，公式仍照常渲染出错（典型：公式里混入中文顿号、全角冒号）；'error' 则会让构建直接失败

5.5 Algolia 搜索（凭据所在）

三条必须记住的规则：

  1. 主题读的是这一份 _config.yml，不是 _config.butterfly.yml。
    证据：node_modules/hexo-theme-butterfly/layout/includes/head/config.pug 里读 config.algolia（appId 也可写成 applicationID）。
  2. apiKey 会被明文写进每个页面的 JS（GLOBAL_CONFIG.algolia）。所以这里必须填 Search-Only Key；填成 Write Key 相当于把写权限公开在网页源码里。adminApiKey 只在执行 hexo algolia 时读取，不会进产物，但也别提交到公开仓库。
  3. 正文用 contentStripTruncate，不要用插件的字段过滤器 content:strip:truncate,0,N。
    后者算出来的键名恰好也叫 contentStripTruncate，而插件是「先 pick 基本字段、再用过滤器结果覆盖同名键」，会把算好的干净正文覆盖回 KaTeX 三层乱码。原因详见 第 8 节。

也可用环境变量覆盖（优先级更高，想避免密钥落盘就用它）：
ALGOLIA_APP_ID / ALGOLIA_API_KEY / ALGOLIA_ADMIN_API_KEY / ALGOLIA_INDEX_NAME。

6.4 横幅与全局背景（本项目核心改造点）

这是全站透明化的完整答案，只有两处容易错：

错误 1：漏了 default_top_img。
Butterfly 的横幅是按页面类型分键取值的：

页面 取值顺序
首页 index_img
归档页 archive_img
单个标签页 tag_per_img[标签名] → tag_img → default_top_img
单个分类页 category_per_img[分类] → category_img → default_top_img
其它页面 page.top_img → default_top_img
文章页 page.cover → page.top_img → default_top_img

而 /tags/、/categories/ 这两个总览页不是 tag/category 类型的页——它们是 type: 'tags' | 'categories' 的普通 page，走的是最后一行。所以只设 tag_img / category_img 时，这两个总览页会继续显示默认色。

错误 2：把值留空（null）。
主题的 getBgPath() 处理逻辑是：

取值 产物
'' 或 null 返回空串 → 不生成内联 style → 回落 CSS 的 #page-header { background-color: $light-blue }（即那块"默认颜色"）
'#fff' background-color: #fff;
图片路径 background-image: url(...)
其它字符串 background: <原样>; ← transparent 走这条

所以想要"透出全局背景图"，必须显式写 transparent，不能留空。

两条横幅的透明效果：

  • 想让横幅彻底不占地（首页内容直接顶到顶部、只剩 60px 导航条）：把 disable_top_img 设为 true
  • 保持 false 时横幅仍占位（首页 100vh、其它页 400px），只是背后是全局背景图——本项目采用这一种

6.8 数学公式

per_page 为什么必须为 true：主题样式里有 .katex { display: none }，要靠 JS 给元素加上 .katex-show 才显示。per_page: false 时该脚本只在 front-matter 写了 katex: true 的文章里加载——漏写这个字段、正文却用了 $...$ 的文章（例如本项目的 MySQL.md）公式会全部隐形，不报错、直接消失。

第二个隐藏条件：主题注入的 showKatex() 选择器是 #article-container .katex。也就是说容器之外的 .katex 元素永远拿不到 .katex-show，永久 display:none。这直接影响摘要——见 第 8 节。

该脚本与 CSS 都是运行时注入的，静态 HTML 里搜不到 KaTeX 的 <link>，只能搜到 classList.add('katex-show') 这段代码。

6.10 字体

字体栈顺序有硬性要求 —— 拉丁等宽字体必须排在中文前面。
Consolas 没有 CJK 字形，代码块里的中文注释必然回退。若把 'PingFang 简体' 排在前面，一旦 'Consolas Web' 加载失败，拉丁字符会被苹方（比例字体）接管，代码会散成非等宽。所以顺序是「本字体 → 各平台系统等宽 → 中文字体 → 兜底」。

自定义字体通过 @font-face 定义在 source/css/custom.css，见 第 7 节。

6.11 图片灯箱

⚠️ 必须小写。模板里是 url_for(theme.asset[theme.lightbox])，而 plugins.yml 的键名是 fancybox / medium_zoom。写成 FancyBox 会取到 undefined → url_for(undefined) = '/' → 生成 <script src="/">：① 灯箱静默失效（点图片不放大）② 浏览器把整个首页当脚本再下载一遍，控制台报 Unexpected token '<'。

6.12 CDN：关键资源自托管

覆盖机制：node_modules/hexo-theme-butterfly/scripts/events/cdn.js 里是

所以只要在 CDN.option 下写 键: /本地路径，就能顶掉对应资源。键名取自 plugins.yml（如 katex / typed / algolia_search）。

为什么把这几项改为自托管：默认走 jsDelivr。一旦该 CDN 在访问者网络下不可达：

资源 加载失败的后果
katex（CSS） .katex 永远停在 display:none，公式整段消失且不报错

7. 自定义样式与字体注入

7.1 注入机制

source/css/custom.css 通过 _config.butterfly.yml → inject.head 以 <link> 注入。.css 文件不会被 Stylus 处理，原样拷贝到 public/css/custom.css，所以可以放心写标准 CSS（写 .styl 反而要走主题变量系统）。

自带样式放在 source/font/，站点路径即 /font/xxx。文件名含空格或中文时，CSS 里必须做百分号转义（见下）。

7.2 三个 @font-face 实例

三个必须遵守的点：

  1. font-weight 只能写 normal。苹方子集只含一个 400 字重；若声明成 100 900 区间，浏览器会认为加粗字重已被覆盖而不再合成加粗，结果是 <strong> 和小标题全部失去粗细对比（已实测）。
  2. src 里文件优先、local() 兜底。把 local() 放前面看着更快，但会导致"装了苹方的电脑用系统版、没装的用 webfont"，同一篇文章在不同设备上字形不一致。
  3. @font-face 名不要与系统字体同名。若把代码字体命名为 Consolas，装了 Consolas 的设备会优先用系统的，你就无法判断 webfont 是否真的生效（排查时会被误导）。

7.3 字体子集化流程（正文字体）

苹方全字集 ttf 10.4 MB → woff2 5.0 MB，而博客实际用字通常只有两三千个。裁剪后体积可降一个数量级（本项目 10.42 MB → 1.12 MB）。

  • 不带 --include-gb2312 时体积约 210 KB，只含站点当前用字；新增生僻字会退回系统字体（字形几乎一致，不会变豆腐块）
  • 带 --include-gb2312 时含 GB2312 全部 6763 个汉字，体积 1.12 MB，日常写作基本无忧
  • 新增文章后：想彻底避免回退，重跑一次（带 --include-gb2312）再部署

7.4 换字体前的标准流程

任何字体在投入使用前，先跑体检，否则很可能遇到"字体静默失效、悄悄回退系统字体"：

它会回答四个关键问题（退出码 0 = 可直接用）：

  1. Chromium 的 OTS 会不会拒绝整个文件？（cmap 子表 language 必须为 0；简单字形 flag 保留位 7 (0x80) 必须为 0）
  2. 有没有「有 cmap 映射但字形空白」的码位？——这种不触发字体回退，浏览器会老老实实画一片空白，比回退还难看
  3. 手工改过字形轮廓的话，hmtx.lsb 与 glyf.xMin 是否同步？（不同步会让字形整体平移）
  4. 是不是等宽（代码字体必须）、ASCII 有没有缺口

反面教材（本项目真实踩坑）：曾用 HELVETI1-1.ttf 当代码字体。它是 Type1 转档产物，Chromium 的 OTS 会拒绝整个文件（cmap language != 0 + glyf flag 保留位 7），字体静默失效；而且 cmap 有 417 个映射却只画了 116 个字形，^ 与 ~ 是空白字形——代码块里的 ~ 出现 36 次、^ 出现 17 次，全都渲染成空白。结论：不要再用它当 web 字体（相关文件 source/font/HELVETI1-1.{ttf,woff2} 与 tools/build-code-font.py 仍保留作参考，custom.css 里已无它的 @font-face）。

等宽度量（判断"用的是不是这个字体"的硬指标）：hmtx.advance = 1126 / upem 2048 = 0.5498 em，95 个 ASCII 字符全部相同。本机 monospace 是 0.5000 em、苹方是 0.5590 em——三者可区分，可用于验证字体是否真的生效。

8. 站点脚本 scripts/：摘要与搜索索引

8.1 要解决的问题

KaTeX 服务端渲染出的 <span class="katex"> 里同时装了三层内容：

  1. <span class="katex-mathml"> —— MathML，给读屏软件 / “复制为 MathML” 用
  2. 其中 <annotation encoding="application/x-tex"> —— 原始 LaTeX
  3. <span class="katex-html"> —— 真正显示的视觉层

主题拿摘要时是 stripHTML(content)，把标签全剥掉后三层文字被拼成一个字符串，于是摘要里同一个公式出现三遍、还夹着原始 LaTeX：

搜索索引里的正文同理，变成 β^(k)\hat{\beta}(k)β^(k) 这种乱码。

8.2 做法

scripts/clean-post-desc.js 在 after_post_render 阶段把每个公式元素整体替换成"它视觉层的纯文本"，一次 flattenMath 产出两份结果：

产物 消费者
data.postDesc 首页卡片 / 上下一篇卡片 / 相关文章的摘要
data.contentStripTruncate Algolia 索引正文（_config.yml → algolia.fields）

几个关键设计：

  • 键名 contentStripTruncate 不是随便取的：主题前端 source/js/search/algolia.js 硬编码依次尝试 hit.contentStripTruncate → hit.contentStrip → hit.content。想自建干净正文，就必须叫这个名字。

  • 强调符还原：\hat / \bar 等在视觉层里的排布是"底字在前、强调符在后"，直接拍平会得到 β^（读起来像"β 的 (k) 次方"）。脚本把"底字 + 强调符"改写成"底字 + 组合音符"，还原成 β̂。

  • 长度上限 3000 字符 + 9000 字节兜底。上限由 Algolia 的单记录大小限制决定，实测（2026-09-24）：

    记录大小 结果
    3000 个中文字 = 7,096 字节 HTTP 201 通过
    5000 个中文字 = 11,828 字节 HTTP 400 Record is too big: size: 11890, maximum allowed: 10000

    即上限 10,000 字节/记录。中文最坏 3 字节/字符，3000 字符 ≈ 9000 字节，再留出 title/permalink/tags 与 JSON 结构约 300 字节，安全。主流教程配置是 500（只够搜到文章开头），本项目取 3000。

  • 加密文章跳过：data.encrypt 的明文不应进公开索引。

  • 不含公式的文章完全走主题原逻辑（if (!data.content.includes('class="katex')) return data），避免产生任何行为差异。

8.3 与主题的关系

主题的 postDesc() 第一句是 if (postDesc) return postDesc，会直接采用脚本算好的结果；文章正文里的 MathML 原样保留，不牺牲可访问性。

想改成手写摘要：把 index_post_content.method 设为 1（只取 front-matter 的 description），脚本的 postDesc 部分会自动跟随；但 contentStripTruncate 不受该开关影响——搜索索引始终需要正文。

9. 如何写作

9.1 新建文章

生成 source/_posts/文章标题.md，以及同名资源文件夹 source/_posts/文章标题/（因为 post_asset_folder: true）。

草稿：hexo new draft "标题"（生成到 source/_drafts/，render_drafts: false 时不会发布），hexo publish draft "标题" 转正。

9.2 front-matter 字段速查

字段 作用 备注
title 标题
date / updated 发布 / 更新时间 updated_option: 'mtime' 时 updated 可省
tags 标签 也可写成列表；影响 /tags/ 页
categories 分类（支持多级） 列表的最后一项是最末级分类
cover 本文章卡片封面 留空则用 cover.default_cover

9.3 正文写作规范（本项目约定）

数学公式（KaTeX）

  • 行内用 $...$，行间独占一行用 $$...$$
  • $ 公式 $ 两侧带空格不会被识别（会渲染成裸 $）
  • $$...$$ 不能写在一行内或句子中间
  • MathJax 的 \( \)、\[ \] 不支持，要换成 $ / $$
  • 公式内不能出现中文标点（顿号、全角冒号、全角括号等）
  • $...$ 内不能写 `{{...}}`——会被 Hexo 当 Nunjucks 标签替换成 swig 占位符（一串 HTML 注释），还原失败后内容丢失、页面显示乱码
  • 强调符直接写 \hat{\beta}、\bar{x}，摘要里会自动还原成 β̂、x̄

图片

三种写法：

  1. 资源文件夹（推荐）——图片放 source/_posts/文章名/，正文里单独占一行写图片引用，括号内只写文件名。配合 post_asset_folder + hexo-image-link 即可正确解析。
  2. 带尺寸控制——直接写 img 标签，src 用相对路径，style 里写 zoom: 67%; 之类（Typora 导出风格也兼容）。
  3. 全站公共图——图片放 source/img/，正文里用 /img/xxx.jpg 这种以 / 开头的绝对路径。

⚠️ 不要在代码块里写图片语法的字面示例。 hexo-image-link 的正则不区分代码块，而它执行时代码块已被高亮成 HTML，贪婪匹配会把标签一起吞进"路径"→ 示例被就地改写成乱码，同时刷一批 Markdown Image Path does not exists!。要举例请像本节这样用文字描述或行内代码。

代码块：正常三反引号 + 语言标识即可。行号、复制按钮、语言标签由主题自动加。行内代码用 `，会套用 code_font_family。

10. 本地预览

10.1 用 tools/serve-local.py，不要用 python -m http.server

为什么不能用 python -m http.server：Python 的 mimetypes 不识别 .woff2 / .woff / .ttf / .otf（guess_type 返回 None），SimpleHTTPRequestHandler 于是回退成 application/octet-stream，并且允许 304 复用缓存。字体加载走的是与 fetch 不同的管线，实际表现是：

或者干脆加载失败、浏览器静默回退到系统字体。排查字体问题时极易误判为"字体文件坏了"，而其实只是服务器的 Content-Type 不对。

本项目的 tools/serve-local.py 补了字体 MIME 并加了 no-store，预览与字体验证都用它。

也可以用 hexo server（npm run server）做日常预览，但验证字体请用前者。

10.2 无头浏览器截图验证（只在必要时用）

想自动化验证渲染结果，可以用无头 Edge / Chrome（注意 msedge.exe 通常不在 PATH 上，要用完整路径，如 "C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe"）：

抓控制台：加 --enable-logging=stderr --v=1，然后 grep INFO:CONSOLE（需过滤 ProtocolLaunch|chrome-extension|Tracking Prevention）。

⚠️ 两个已知失真，务必警惕：

  1. 动画类效果会被"洗白"。全局背景图 #web_bg 带 bg-animation（to_show 4s 淡入）。无头环境若某个 jsDelivr 请求挂起（无代理时），网络不 idle → 虚拟时钟不推进 → 动画停在开头，背景图近乎不可见（本地中位亮度 199，而线上是 52）。曾因此误判页脚对比度只有 1.08:1 并错误地改了页脚文字颜色（线上实拍显示深色字压在深色夜景上更糟，已撤回）。
    规避：探针里强制终态 —— b.classList.remove('bg-animation'); b.style.opacity = 1。
  2. 无头渲染结果不能替代线上实拍。涉及颜色/对比度/动画的判断，最终以线上截图为准。

12. 部署

12.1 标准流程

hexo deploy --generate 可以合并步骤 2 和 5（先 generate 再 deploy）。

12.2 hexo deploy 到底做了什么

  1. 找到 deploy 配置里的 type: git
  2. 若 .deploy_git/ 不存在就 git init 并配置 remote
  3. 把现有 public/ 整个拷进 .deploy_git/（提交信息形如 Site updated: 2026-09-24 11:36:52）
  4. commit + push 到远端 main 分支

关键点：

  • hexo deploy 不会重新 generate。如果你改了文章却没 generate，部署上去的还是旧内容
  • 首次 push 可能耗时较久（整个 public/ 要传），后续是增量
  • 想强制重建远端历史：删掉 .deploy_git/ 再 deploy

12.3 首次配置仓库

.deploy_git/.git/config 里会自动写好 remote。若需手改，直接改 _config.yml 的 deploy.repository 然后删掉 .deploy_git/ 重新 deploy。

12.4 自定义域名（可选）

  1. 在 source/ 下建 CNAME 文件（无扩展名），内容只有一行域名，如 blog.example.com
  2. 域名商处加 CNAME 记录指向 <用户名>.github.io
  3. GitHub 仓库 → Settings → Pages → Custom domain 填同一域名，勾选 Enforce HTTPS
  4. _config.yml 的 url 改成 https://blog.example.com，然后重新 generate + hexo algolia + deploy（url 变了，索引 permalink 也要刷新）

12.5 部署排错

现象 原因 处理
Recv failure: Connection was reset HTTPS push 被掐 换成 SSH 地址
Permission denied (publickey) SSH 密钥未配或未加到 GitHub 重做 1.2
推上去了但页面没变 忘了 generate（deploy 不重新生成） hexo clean && hexo generate && hexo deploy
页面 404 但文件在 仓库设置或分支不对 确认推的是 main、Pages 源指向该分支根目录
整站无样式 Stylus 编译失败，index.css 为 0 字节 查 code_blocks.theme 等枚举值是否非法；清缓存重建
搜索能搜到但点进去跳 example.com url 还是占位值 改 url → 重新 hexo algolia + deploy

13. 必避的坑（汇总）

按"踩到的概率 × 排查难度"排序。

坑 1：改主题配置后必须清缓存

Hexo 把渲染结果缓存在 db.json，hexo generate 不会重编译主题 CSS，会继续沿用旧产物（表现为"改了配置页面没变化"）。删 db.json（或 hexo clean）后重新生成。

坑 2：Stylus 编译失败只报一行 ERROR、不中断构建

产物是 0 字节的 public/css/index.css，整站无样式，但 hexo generate 退出码仍是 0。触发原因多为枚举值非法（如 code_blocks.theme: light 之外的怪值）。
务必确认 public/css/index.css 体积正常（约 230 KB）。

注意 public/css/var.css 为 0 字节是正常的（主题 var.styl 只定义变量、无选择器，编译本就无输出）。

坑 3：front-matter 的 key: value 冒号后必须有空格

写成 cover:\path\... 会让整个 front-matter 解析失败，该文章静默沿用旧产物（构建日志里只有一行 ERROR Process failed: _posts/xxx.md，退出码仍是 0）。每次构建后都 grep -c ERROR 一下日志。

坑 4：本地预览 / 验证字体必须用 tools/serve-local.py

python -m http.server 不认识字体 MIME，会回退成 application/octet-stream，字体加载管线直接拒绝，表现为"字体静默失效"。极易误判成"字体文件坏了"。

坑 5：url 留成 example.com

同时污染 canonical / og:url 与 Algolia 索引里的 permalink，表现为"搜索能搜到，但点进去跳到 example.com"。

坑 6：主题配置的 lightbox 大小写

必须写 fancybox（或 medium_zoom）。写成 FancyBox 会生成 <script src="/">：灯箱失效 + 浏览器把首页当脚本下载，控制台报 Unexpected token '<'。

坑 7：横幅"透明"必须显式写 transparent，且不能漏 default_top_img

见 6.4。留空会回落到主题的默认色块；/tags/、/categories/ 总览页走的是 default_top_img 而不是 tag_img/category_img。

坑 8：@font-face 的 font-weight 不能写区间

字体文件只有 400 一个字重时，声明 100 900 会让加粗全部失效（浏览器认为该区间已被覆盖，不再合成加粗）。

坑 9：markdown_it_plus.plugins 的缩进层级

name / enable / options 必须嵌套在 plugin: 之下，平铺写法会让选项静默失效。用 verify-plugin-options.js 核实。

坑 10：不要用 content:strip:truncate 当搜索正文

插件的字段过滤器会覆盖 clean-post-desc.js 算好的干净文本，把三层 KaTeX 乱码塞回来。

坑 11：KaTeX 的隐藏前置条件

math.per_page 必须 true；且 showKatex() 只作用于 #article-container .katex——容器之外的公式永远 display:none。所以摘要里的公式必须整体替换成纯文本，不能只剥标签。

坑 12：无头渲染会因动画被拖住而"洗白"

见 10.2。涉及颜色对比度的判断必须看线上实拍。

坑 13：subtitle.source 填了网址而不是数字

source 是 Pug case/when 的数字枚举（1 / 2 / 3 / false），填 https://www.jinrishici.com/ 会落到 default 分支：一个接口都不请求，只显示 sub 的兜底文字，不报错、不写 console。详见 6.6。

坑 14：写了枚举但没清缓存，产物仍是旧的

改完主题配置后必须删 db.json（或 hexo clean）再生成，否则产物里还是旧分支。check-subtitle.py 的 C 项专门检测"配置合法但产物里搜不到对应调用"，会直接提示这一点。

配置项 默认值 本项目 理由
主题安装位置 themes/ node_modules/ npm 管理，升级方便；自定义走 inject + scripts/

lightbox 空 fancybox 点图片放大（注意小写）

源站版本控制 建议纳入 未纳入 只有 public/ 经 .deploy_git/ 上 GitHub
